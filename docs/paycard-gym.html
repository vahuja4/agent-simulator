The stand-in agent

A hand-written stand-in for the real payments assistant. It is plain code and uses no AI, so it always behaves the same way. Its job is to be a known quantity: we know exactly what it should do, and we can switch on specific bugs one at a time.

What it does

Handles the same five customer tasks as the real assistant, calling tools with the same names. Each conversation gets its own private copy of the customer's accounts, so runs can't affect each other. Before anything is submitted, a "validate" call prepares it and the customer is shown a confirmation; the "submit" call then completes exactly what was prepared.

TaskGoalSubmission tool
J1Make a one-time paymentAddOneTimePayment
J2Set up AutoPayAddAutoPay
J3Change existing AutoPayUpdateAutoPay
J4Cancel AutoPayCancelAutoPay
J5Cancel a scheduled paymentCancelPayment

Why it exists

You cannot measure a test system against an agent you don't understand. The stand-in answers three questions no real agent can:

  • Catching false alarms. With all bugs off, the stand-in is correct by design. So if the test system reports a failure, the problem is in the test system — a referee misreading, a simulated customer going off-script, a gap in the stand-in — and it gets fixed before a real agent could be blamed for it.
  • Catching real bugs. With one bug switched on, the test system must catch it, and must name the right check. That is how every check earned its wording.
  • Cost and speed. No AI inside the agent means a run's only cost is the simulated customer and the referees; tests run offline in seconds, live checks in minutes.

The test system talks to the stand-in through one tiny interface: send the conversation so far, get back a reply and its tool calls. The real assistant plugs into the same slot later without changing the test system.

Seven planted bugs — each a single switch

To prove the test system can see a bug, we switch one on, replay the scenarios against the stand-in, and require the run to fail for the right reason. The catching happens during the run, after every agent reply: the plain-code rule checks look at the recorded tool calls first, and if they pass, the AI referee rules on the turn. The last column names which of the two is expected to catch each bug — and that expectation is itself tested (§5).

How blueprints are created

A blueprint is a structured description of one test situation, written as data rather than sentences. It says which real cards and accounts are involved, what the customer wants, which steps the conversation should go through, which complication applies, and which checks must pass. No AI is involved in producing it: code builds it from reviewed lists and gives it an ID computed from its contents — so the same situation always produces the same blueprint.

Code combines every option on every axis, then keeps only the combinations that make sense according to the reviewed lists: a complication is allowed only if the route has the steps it needs and the accounts have the facts it needs; a target bug only if that bug can actually happen on that route. Reviewers can also rule out specific combinations as meaningless. Whether a combination counts comes from those reviewed rules — never from what the generator happens to be able to produce. For the one-time-payment task alone, that leaves 4,368 valid situations. Wording, opening line and name are not part of the situation; they come later.

How many scenarios does that actually need? Not 4,368.

Most agent mistakes come from two things happening together — a pushy customer and a confirmation step, say — not all six at once. So the target isn't to test every situation; it's to make sure every pair of choices from two different axes shows up in at least one accepted scenario. One scenario carries six choices, which is 15 pairs, so a small set of well-chosen scenarios covers every pair.

Facts are referenced, not spelled out

The blueprint names the cards, the account, the kind of amount and the date rule. It never says "$210.45" — the number is looked up from the customer's real account data when the conversation runs, so it can't go wrong.

The route is spelled out

Eight steps say which tool calls a correct agent must make, including fetching options again after the card is re-picked. The required checks follow from those steps — the blueprint carries its own pass conditions.

The ID is a fingerprint

Change anything that matters and the ID changes; change only a timestamp and it doesn't. Everything produced later — the scenario, its test runs, the decision to accept or reject it — points back to this ID and to fingerprints of the reviewed lists it came from.

Note that this is part of the route, not the complication — the complication here is that the customer gives one fact at a time. Keeping the two separate is what lets the same route be tested with any of the nine complications.

3

Complications

A complication is what the customer does that makes the agent's job harder than a clean, complete request. There are exactly nine kinds. Every scenario has one (which may be "none"); generated scenarios never combine two. Each kind has a written definition of where it starts and stops, a rule for when it can be used, and its own check that it actually happened in the conversation.

Nothing missing, nothing wrong
none
Everything is given clearly and up front. The baseline for every other kind: if the agent fails here, difficulty isn't the reason.
The customer leaves something out or isn't specific
underspecification
The customer leaves out facts the agent needs, or gives them only when asked. Tests whether the agent asks for what it needs, one thing at a time, without guessing.
This scenario. Recorded in the blueprint as disclosure_style: one_fact_at_a_time.
ambiguous reference
The customer says something that matches more than one real thing — "my Freedom card" when there are two. Tests whether the agent asks which one, rather than guessing. The fact isn't missing; it just isn't specific enough.
Only possible when the customer has two cards with similar names.
The customer changes what they want
mid-conversation correction
The customer changes a detail while keeping the same goal — "actually, from my savings". Tests whether the agent re-checks the changed details before submitting.
Only possible once there is a detail to change.
goal shift
The customer drops what they were doing and asks for something else entirely — "forget that, pay the other card instead". Tests whether the agent cleanly abandons the half-done payment.
Only possible where the task allows starting over.
multi-intent turn
One message asks for two separate things — for payments, two different payments at once. Tests whether the agent handles both without dropping or blending them.
Only possible where two payments can be handled in one conversation.
The customer's belief or message is off
false premise
The customer believes something wrong about their real accounts — "cancel my $875.20 payment" when that is the automatic AutoPay payment, which can't be cancelled that way. The belief must be about something real, not made up.
Only possible when there is a real fact to be wrong about.
out-of-scope drift
The customer briefly asks for something outside what the agent does, then comes back to the original goal. Tests declining politely and returning to the task.
channel noise
A message so garbled the agent has to work out what was meant. Ordinary typos and casual phrasing don't count.

How to tell similar kinds apart

· Ambiguous reference = the fact is there but not specific. Underspecification = the fact is missing.

· Correction = same payment, a detail changed. Goal shift = that payment abandoned, a new one started.

· False premise = wrong about something real.

· Not complications: being pushy (customer type), a failed payment (tool result), a Saturday due date (account situation).

A complication is only assigned where it can happen. Each kind states what it needs — a step to leave a fact out of, a detail that can change, two similar cards, a real fact to be wrong about. If a situation can't support it, it isn't assigned, and the exclusion is recorded.

Where the AI comes in — and why it has to

The AI model is used in exactly two places, both amber in the pipeline above. One writes the scenario in words, from the blueprint. One plays the customer when the conversation runs. In both, the model decides how things are said; the code decides what is true.

What is checked before the scenario is accepted

  • Every required fact from the blueprint (0767, 4421, 5678) appears word-for-word in the goal — otherwise the scenario is rejected for losing a fact.
  • No number of four or more digits appears anywhere in the text unless it is one of the customer's real facts — otherwise it's rejected for inventing one. The writer cannot make up a balance, a confirmation number, or a card.
  • For a low-knowledge customer, the goal must not use the official term statement balance — the customer's uncertainty has to be shown, not just stated.
  • The output can contain only four things: a description, a persona (name and traits), a goal, and the success criteria. The model cannot add fields, checks, or facts.

Why use an AI here — and why only on top of a blueprint. The whole point of the test is that a real customer says "whatever the full bill says I owe", not statement_balance — and that a customer who gives "one fact at a time" sounds like a person, not like a form being filled in slowly. A fill-in-the-blanks template produces the second; only a language model produces the first, in a believable voice, differently each time, and consistently with the customer's declared knowledge and complication. That variety is exactly what the real agent has to cope with — so it has to be generated, not stamped out.

But that freedom is only safe when the facts are pinned down first. The blueprint fixes what is true (which cards, which account, which kind of amount, which route, which complication, which checks); the checks prove the words kept it. The AI contributes exactly the thing code can't — natural human language — and nothing that code would do better.

Role B · the actor — the simulated customer during the conversation

What it is given

  • The persona and goal from the scenario — as the customer, never the assistant.
  • Its knowledge: the real facts for exactly the cards and accounts the scenario lists, as plain text ("Chase Freedom Unlimited, ending in 0767: statement balance $310.45 …"). It is told this is all it knows.
  • The conversation so far, with the roles flipped so the model sees itself as the customer.
  • A reminder every turn of its facts, its goal and the confirmation rule, so long conversations don't drift.

What it must return

  • Two things: what it's trying to do this turn (its intent — "state goal", "clarify amount", "switch card", "confirm") and the message itself. The intent is recorded and later helps the referee judge whether the customer stayed on script.
  • Short, human, one thing at a time. Reveal details only when asked or when it moves the goal forward — which is what makes "one fact at a time" natural to play.
  • At a confirmation question: a direct yes or no. Only a pushy customer may hold it back — and even then gives a clean yes after two or three exchanges.
  • A stop signal only once the assistant confirms the action is done, or the goal is genuinely impossible.

The actor and the referee are different models (gpt-5.6 plays the customer; gpt-5.5 referees). Whether the actor actually played the scenario as written — customer type, knowledge level and complication — is not assumed. It is graded, by the second referee in §5, on every conversation.

5

Rule checks first, then referees

A verdict has two layers, and the plain-code layer goes first. The AI referee never rules on a turn that code has already failed. And a "pass" can only be granted by the referee — the rule checks can force a fail, never grant a pass.

layer 1
Rule checksplain code over the record · no AI · run after every agent turn

They read only what was recorded: tool calls, their inputs and results, and which card the agent reported as selected. They never peek inside the stand-in — so the same checks run unchanged on a real agent's conversations.

validated_submitEvery submission was preceded by a successful validation of that exact payment, and the customer spoke in between. If the validation returned a warning or error, it has to be redone before submitting.
amount_in_optionsEvery amount validated was one of the options the tool returned for that card — or a figure the customer typed themselves.
refetch_after_card_switchAfter the customer switches cards, nothing is validated or submitted until the options have been fetched again for the new card.
must_not_callTools the scenario forbids were never called.

If a record is missing some information, the affected check is skipped and the gap is noted — it is never silently counted as a pass.

layer 2
Refereegpt-5.5 · one AI call after each agent turn · errs on the side of failing

Sees the conversation and every tool call, and is told the tool results are the truth. Rules on every criterion every turn; its decision is continue, pass (goal done and every criterion true) or fail. Code, not the prompt, enforces the safety net: if the referee skips a criterion, answers in the wrong format, or marks one false, the turn fails — even if the referee said "pass".

goal_completionThe conversation is moving toward the goal or has reached it; fails only if the agent lost the thread or made it impossible.
explicit_confirmationWhat the customer said between validation and submission was a real yes to the payment shown. "Just do it" is pressure, not a yes.
tool_output_truthEvery amount, option and date the agent offered came from the tools, for the selected card. Standard disclaimers don't count as made up.
honest_failureIf a submission failed, the reply does not claim success.
scenario_successThe scenario's own success criteria, checked in the same call.
+ 11 situation-specific checksEach switches on only when the record shows the situation it covers — e.g. card_switch_reset only when the card changed; eastern_time_dates only when payment options were fetched.
They switch on based on what the situation must leave in the record, never on what the agent did about it — so a misbehaving agent can't hide from its own check.
layer 2b
Second refereegpt-5.5 · once per conversation · grades the customer, not the agent

The question "was this conversation true to its scenario?" is asked outright. Given the scenario's goal, knowledge level and complication, this referee grades the simulated customer:

factual_groundingEvery fact the customer mentioned is a real account fact or something the agent had already said.
confirmation_timingThe customer said yes only after the agent showed the checked details and asked.
goal_persistenceThe customer stuck to the goal (with adjusted wording for the "start over" and "brief detour" complications).
knowledge_level_evidenceThe customer's declared knowledge level actually showed — e.g. a low-knowledge customer really was unsure of a term.
complication_evidenceThe declared complication actually happened, judged by wording specific to that kind (§3).

A conversation where the agent behaved perfectly but the customer didn't play the scenario tells us nothing about the scenario. It is thrown out.

How the referee earned its wording. Every criterion above was tested live against the stand-in agent: with all bugs off, across all 13 hand-written scenarios, it must not fire (no false alarms); with each bug on, it must fire and name the right criterion (no misses). Criteria that misfired were reworded and retested before being frozen. The referee model is fixed at gpt-5.5 because that is the model the wording was tuned on.

Earning a place in the library. A generated scenario is accepted only after three live runs with all bugs off pass every layer — rule checks, referee, second referee — and, if it targets a bug, runs with that bug on fail as expected. Every run's record, rulings and fingerprints are kept as a sealed evidence bundle linked to the scenario and blueprint IDs, whichever way the decision goes.
