Perturbations vs Complications

One tangible win: given any test difficulty, you can say which taxonomy it belongs to, which value it is, and why the repo refuses to mix the two.

The boundary, in one sentence

ADR-0005, verbatim

"Procedure branches, validation outcomes, tool failures, and fixture conditions are not conversational Complications."

The intuition: a perturbation changes what happens — the flow, the data, the tool outcomes. A complication changes how the customer talks or what they believe. A payment that fails because it's $6,000 is mechanics. A customer who says "my Freedom card" when they own two Freedom cards is conversation. Same chat can carry both.

The razor cases (straight from ADR-0005)

Ambiguous-reference ≠ underspecification: supplying a colliding fact vs omitting a fact. Correction ≠ goal-shift: preserving vs abandoning the instruction — "parameter count is never the discriminator." And the trap: a below-minimum request made with correct knowledge is none — the warning is a journey/fixture condition, i.e. perturbation territory.

How a complication becomes checkable: journey events

The three hardest complications don't stay prose — they bind to events now defined in the graph itself (procedures/j1.yaml, events: block), each with countable semantics:

EventGoal relationshipInstructions / completedState transition
correctable-parameter-suppliedpreserved1 / 1revalidate-amended-instruction
j1-abandon-replace-payment-goalabandoned-and-replaced2 / 1discard-abandoned-instruction
j1-two-payment-intents-one-turnindependent-same-turn2 / 2preserve-independent-instructions

Read the middle column as the discriminator made machine-checkable: correction = one instruction ends completed; goal-shift = two instructions, only the replacement completes; multi-intent = two instructions, both complete. The contract's required_event_ids points at these.

Where each lives in a blueprint

Two synthesis generations, two homes:

  • Phase 4.1 blueprint (enumerate.py): carries a perturbations: list (≤2 entries of type+position). No complication field exists here.
  • Phase 4.5 CoverageBlueprint (generator.py / planner.py): complication is one of the six axes of a coverage cell — journey path × persona archetype (cooperative/pressure/vigilant/persistent) × knowledge level (high/medium/low) × complication × fixture state class × fitness target. The planner sweeps cells; each cell becomes one test.
