The rules that bound the set

  • Finite by declaration. 5 types, 6 declaration sites. The graph file is the single authority; blueprint.py stores only (type, position) strings and the validator checks them against the traversed edges.
  • Journey-specific, twice. Graphs are per-journey (only J1 exists today → J2–J5 have no perturbations yet), and within a journey each perturbation is pinned to specific edges, not "anywhere".
  • At most two per blueprint (MAX_PERTURBATIONS = 2 in enumerate.py), so a failing test points at a clear cause.
  • Compiled into the customer. _goal_facts() turns each into a customer habit, a data binding, or an amount — never a script for the assistant.
  • Parked ≠ deleted. The two validation types are declared (the journey defines those outcomes) but marked non_executable_against: mock; blueprints using them are parked in generated_scenarios/unexecutable_blueprints/ with the reason.
  • How the set grows. A new documented journey behavior or observed customer shape → a new edge declaration with an executable trigger. Never a free-form addition (the graph "must be derived from the approved journey definitions").
Not the whole story

Perturbations cover journey/data mechanics only. The repo has a second closed axis for conversational difficulty — the nine-value complication taxonomy (ADR-0005): "Procedure branches, validation outcomes, tool failures, and fixture conditions are not conversational Complications."
